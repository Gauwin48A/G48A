## 3. SECURITY NEGATIVES — SERVER

### 3.1 Test Mode Secret Exposure (CRITICAL)
**File: `server/src/controllers/authController.js`**
```js
if (process.env.NODE_ENV === "test" && process.env.AUTH_EXPOSE_TEST_SECRETS === "true") {
  responsePayload.resetToken = resetToken;
  responsePayload.otp = otp;
}
```
**Risk**: If `AUTH_EXPOSE_TEST_SECRETS=true` is accidentally set in production, OTPs and reset tokens are returned in API responses — complete authentication bypass.
**Missing**: No CI/CD guard prevents this flag from being active in production.

### 3.2 Hardcoded Development Credentials
**File: `server/src/config/db.js` (L59)**
```js
const dbPassword = readEnv("DB_PASSWORD", isProduction ? undefined : "password");
```
- Default DB password of `"password"` in development encourages weak local security practices.

### 3.3 Weak WAF Regex — False Positive Risk
**File: `server/src/middleware/wafEnforcement.js` (L9)**
- Pattern `/--\s/` blocks SQL comments but also blocks legitimate text like "well -- anyway" in descriptions.
- Users posting technical content may get blocked unexpectedly.

### 3.4 Rate Limiter Uses In-Memory Store
**File: `server/src/middleware/rateLimiter.js` (L19)**
```js
// IP counts stored in Map()
```
- Memory store resets on every server restart — attackers just need to wait for a deploy.
- In clustered PM2 mode, each worker has independent rate counters — attacker can distribute across workers.
- **Fix**: Use Redis for distributed rate limiting.

### 3.5 Login Limiter — Local Memory Only
**File: `server/src/middleware/security.js`**
- `loginLimiter` (5 attempts/15min) uses local memory — resets on server restart.
- Doesn't share state across PM2 cluster instances.

### 3.6 XML Upload — XXE Risk
**File: `server/src/middleware/upload.js` (L84-92)**
- `application/xml` is in the allowed MIME types.
- If uploaded XML is ever parsed server-side, this enables XML External Entity (XXE) attacks.

### 3.7 Loose Token Verification
**File: `server/src/middleware/auth.js` (L23)**
- `verifyCandidateToken` catches ALL errors and returns `null`, losing specific failure context.
- A token verification error and a missing token produce the same result — makes debugging difficult.

### 3.8 CORS Empty Origin Allowed
**File: `server/src/index.js` (L209)**
- `isOriginAllowed` returns `true` for empty origins, potentially allowing non-browser requests to bypass CORS.

### 3.9 Error Handler — Stack Trace Exposure
**File: `server/src/middleware/errorHandler.js` (L75)**
- Full stack trace and `rawError` exposed when `NODE_ENV` is not exactly `"production"`.
- Any typo in NODE_ENV (e.g., `"Production"`) exposes internals.

### 3.10 JWT Secret in CI/CD YAML
**File: `.github/workflows/auth-integration.yml` (L39)**
- `JWT_SECRET` is in plain text in the workflow file, not GitHub Secrets.
- While test-only, it sets a bad pattern that could be copied for production secrets.

## 4. SECURITY NEGATIVES — CLIENT

### 4.1 localStorage for Tokens
**File: `client/src/context/AuthContext.jsx` (L34)**
```js
// authToken and refreshToken stored in localStorage
```
- `localStorage` is accessible to any JavaScript running on the page.
- If any XSS vulnerability exists, tokens can be stolen.
- Server already sets `HttpOnly` cookies — the localStorage fallback weakens the auth chain.

### 4.2 Client-Side Fraud Prevention Bypassable
**File: `client/src/utils/fraudPrevention.js`**
- `generateDailySecretCode` and `validateSecretCode` run entirely client-side.
- An attacker can read the algorithm from source and generate valid codes.

### 4.3 Global Override Attack Surface
**File: `client/src/services/api.js`**
- `window.__MHUB_API_ORIGIN_OVERRIDE__` allows runtime API origin changes.
- A malicious browser extension or XSS could redirect all API calls to an attacker's server.

### 4.4 Security Headers via Meta Tags
**File: `client/index.html`**
- `X-Content-Type-Options: nosniff` set via `<meta http-equiv>` — not enforced by all browsers.
- These headers must be set at the server level (Nginx/Vercel) for proper enforcement.

### 4.5 ESLint Security Rules Disabled
**File: `client/eslint.config.js` (L30-32)**
```js
'no-unused-vars': 'off',
'react-hooks/exhaustive-deps': 'off',
```
- Disabling `react-hooks/exhaustive-deps` hides stale closure bugs.
- Disabling `no-unused-vars` hides dead code and potential import leaks.

### 4.6 Hardcoded Canonical URL
**File: `client/index.html` (L15)**
- `https://example.com` as canonical link — should be the actual production domain.
**File: `client/public/sitemap.xml` (L4)**
- Same `https://example.com` in the sitemap.

## 9. CODE QUALITY — SERVER SERVICES

### 9.1 In-Memory State — Lost on Restart (Multiple Services)
| Service | Data at Risk |
|---------|-------------|
| `securityTrustOpsService.js` | Security incident tracking (`incidentsById` Map) |
| `riskTelemetryService.js` | Risk decision history |
| `telemetryPipelineService.js` | Dedupe cache (`dedupeCache` Map) |
| `socketService.js` | User-to-socket mapping (`userSocketMap`) |
| `rateLimiter.js` | IP request counts |
| `activityTracker.js` | User activity cache |

- All this data is lost on server restart or PM2 restart.
- In clustered mode, each worker has independent state — creates inconsistencies.

### 9.2 Potential OOM — Unbounded Caches
**File: `server/src/services/telemetryPipelineService.js`**
- `dedupeCache` (Map) grows indefinitely if `TELEMETRY_DEDUPE_TTL_SECONDS` is set too high.

**File: `server/src/services/tokenVerificationCache.js`**
- LRU cache can grow large under high-traffic conditions if sweep interval is too slow.

### 9.3 DDL at Startup — Race Condition
**File: `server/src/services/schemaGuard.js` (~380 lines)**
- Runs `ALTER TABLE` to add missing columns at startup.
- In multi-instance PM2 environments, two instances starting simultaneously can race on DDL operations.

### 9.4 Floating Promises
**File: `server/src/services/fleetOrchestrationService.js`**
- Uses `void runQuery(...)` in some loops — unhandled promise rejections can crash the process.

### 9.5 Hardcoded Intervals
Multiple services hardcode expiry times and thresholds:
```js
// OTP expiry: 10 minutes (hardcoded)
// Activity tracker: 5 minutes (hardcoded)
// Cache sweep: 60 seconds (hardcoded)
```
- Should be configurable via environment variables.

### 9.6 Deep Referral Recursion Risk
**File: `server/src/services/referralChainRewards.js`**
- Deep recursion in chain processing could cause stack overflow for very long chains.
- Should have an explicit depth limit enforced at the query level.

### 9.7 2FA Logic Divergence
- `twoFactorPolicyService.js` and `twoFactorValidationService.js` have slightly different fallback table handling.
- Should be consolidated into a single 2FA provider.

### 9.8 Socket Cleanup Leak
**File: `server/src/services/socketService.js`**
- `userSocketMap` entries are never cleaned up if the `disconnect` event fails to fire (e.g., process kill, network timeout).
- Stale entries accumulate over time.

### 9.9 Phone Number Country Code Assumption
**File: `server/src/services/twoFactorPolicyService.js`**
- `prefixedPhone` logic hardcodes `+91` (India).
- Will fail silently for users with other country codes if the platform expands internationally.

### 13.2 Migration Number Collision


### 13.3 INT vs UUID Conflict — The "ID Mismatch" Bug
**Critical architectural issue across the codebase:**
- `MHUB_ULTIMATE.sql` uses `SERIAL` (integers) for primary keys.
- `defender_schema.sql` and newer migrations use `UUID`.
- Many controllers use `::text` casts to bridge the gap:
```sql
WHERE p.user_id::text = u.user_id::text
```
- Test files mock `userId` as string (`'user-1'`) which fails with UUID expectations.
- Verification fields return `NULL` because of this mismatch.

### 13.4 No Migration Tracking Table
- No `schema_migrations` or `knex_migrations` table.
- No way to know which migrations have been applied.
- Scripts rely on manual execution order — dangerous for team environments.

### 13.5 Broken Migration References
**File: `server/scripts/migrate.js`**
- References `migration_add_location_columns.sql` which was deleted from `database/`.
- Migration paths are stale after reorganization.

### 13.6 Destructive Migration Scripts
**File: `server/database/migrations/defender_schema.sql`**
- Drops `login_history` and `transactions` tables to recreate them — causes data loss.

### 13.7 Seed Data Brittleness
**File: `server/database/seed_data.sql`**
- Hardcoded IDs and specific user emails.
- Many posts have identical timestamps — "Sort by New" tests meaningless.

### 13.8 Missing Cascading Deletes
- Some newer audit tables lack `ON DELETE CASCADE`.
- Orphaned records when parent records are deleted.

### 17.6 locationService UI Thread Blocking
